# 分类型逐文件闭环规程

本规程用于六群新文件直做、财务重发纠错和生产表补全。它不是分类说明，而是 Agent 在识别出文件内容后必须执行的完整业务闭环。每个文件先拆成 0/N 个稳定事实；每个事实分别完成专业表补全、正向和反向搜索、原件逐候选核验、业务表级联以及写后验证。

## 1. 通用处理外壳

### 1.1 接收和冻结来源

对每个群文件先保存不可变来源信息：消息事件 ID、群 ID、文件 Token、原文件名、发送时间、文件大小、MIME、下载结果和 SHA。相同 SHA 的重发仍是一个新的来源事件；如果文件名含新映射，必须处理该映射，不能因内容重复而跳过。

写入或更新文件索引时保留：原始对象、派生对象、父子血缘、内容哈希、版本组、可读性、分析状态、事实数、文件类型集合、映射解析结果和最终处理结论。不得让一个“主分类”掩盖复合文件中的其它事实。

### 1.2 完整读取

- PDF：先取文本层作候选，再渲染并视觉查看封面、主体页、金额页、业务条款页、签章页及所有包含事实的页面。
- Word：读取全部正文、表格、页眉页脚和嵌入图片，并渲染检查版面与签章。
- Excel：遍历全部非空 sheet、有效区域、公式显示值、隐藏的业务页和打印区域；不能只读首表。
- 图片：查看原图；分辨率不足时记录不可读字段，不猜测。
- 压缩包：安全解包，成员逐个成为派生对象；容器本身通常不产生重复业务事实。
- 多单据文件：按真实单据或事件边界切割派生对象，同时保留父文件。

#### PDF 视觉假空白硬门

页面只显示底图、表格、印章或水印，而交易文字、合同正文等缺失时，不得据此判定“空白文件”“原文未载明”或要求补件。按以下顺序交叉验证：

1. 提取原始文本层并统计字符；检查页面内容流、字体资源、表单字段/注释、可选内容层和嵌入图像。
2. 检查文字颜色、裁剪、透明度和坐标是否异常；重点识别未嵌入字体及字体替代失败，例如中文 `Type0/CIDFont` 仅引用系统字体而未随 PDF 嵌入。
3. 至少使用另一条独立链路重新渲染或解析。文本层存在稳定字段而首轮位图缺字时，把首轮结果记为“渲染兼容失败”，不能记为原件缺失。
4. 对从文本层恢复的关键字段仍需用可正确显示文字的替代渲染、局部截图或其它原件表现形式完成视觉核验；在完成前标为“文本候选待视觉确认”，不得伪称已视觉确认。
5. 若多条独立链路均证明内容确实不存在或不可恢复，才可写“原文未载明/页面不可读”，并记录所用工具、失败现象和补件要求。

典型情形：银行电子回单的模板、印章是图片，付款人、账号、金额和流水号使用未嵌入中文字体。某些渲染器只画出图片而漏掉文字，但文本解析器仍能提取完整交易字段。这是“视觉假空白”，不是空白回单。

### 1.3 先观察，再形成事实

对原件先输出：页面结构、出现的主体、单据标题、日期、金额、编号、账号、项目、签章、空白栏和冲突。随后提出可被原件反驳的业务假设，再提取 0/N 个稳定事实。

稳定事实不因“尚未签章”自动归零。例如未签合同仍可形成“合同草案/未生效合同事实”；空白验收模板只形成模板证据，不能形成已验收事件；双方盖章但验收结论空白的验收单可以证明双方曾制作或签章该单据，但不能证明验收合格。

每个字段记录证据页或对象、读取方式和状态：已视觉确认、文本候选待视觉确认、原文未载明、页面不可读、不同页面冲突。禁止用一个总置信度代替字段级证据。

### 1.4 分解复合文件

一个文件出现合同、发票、回单和验收单时，建立一个文件索引对象和多个专业事实。每个事实独立生成事实 ID、专业表动作和关系闭环；共享同一来源文件集合，但不得只按文件名选择一个表。

### 1.5 生成闭环计划

每个事实的 Action Plan 至少包含：

1. 要新建、归并或补全的专业表记录。
2. 要搜索的其它事实表及搜索方向。
3. 候选召回条件、硬排除条件和必须打开的原件。
4. 可确认、只能候选、明确拒绝或确认缺失的关系。
5. 受影响的项目、项目流水汇总、合同收付款审核和四流一致审核记录。
6. 写前快照、写后回读、幂等和回滚动作。

## 2. 全类型共用的候选搜索和强匹配标准

### 2.1 先广泛召回

候选召回是为了避免漏掉，不代表确认。按文件类型组合使用：

- 本公司完整法定名称、历史名称、可证明的简称和本公司账号；
- 交易对象完整名称、别名、税号、账号和被证明的代收代付关系；
- 业务角色与资金方向；
- 合同号、回单号、流水号、发票号、项目号等强键；
- 项目名称、地点、品类、设备型号、服务内容；
- 业务日期、合同生命周期、付款节点、开票和履约时间；
- 单笔金额、含税/未税关系、分期金额、累计金额池、退款和冲正净额。

日期窗口必须来自业务逻辑，不使用固定天数机械匹配。签约后预付款、交货后尾款、验收后付款和质保尾款各有不同窗口；出现明确证据时允许签前保证金或先行付款。

### 2.2 再执行硬排除

按以下顺序排除，任一硬冲突成立就不能被金额相似或评分推翻：

1. 本公司法定主体不对，且没有已证实的集团代付、代收或债权转让链。
2. 业务角色或资金方向相反。
3. 交易对象不对，且没有代理、平台结算、个人经办或第三方支付证据。
4. 回单摘要、合同号、发票号或文件名映射明确指向别的业务。
5. 日期在业务生命周期上不可能成立。
6. 项目、地点、品类或设备强冲突。
7. 该事实已被另一闭合关系全额占用，继续复用会造成无依据重复计额。
8. 红冲、退款或冲正方向被当成新增收入或成本。

### 2.3 对剩余候选逐个打开原件

Agent 必须逐个打开源事实和候选事实的关键原件，逐项对比：主体、角色、方向、账号、编号、摘要、项目、品类、日期节点、金额结构、签章和已占用金额池。只看表格摘要、OCR、标题或脚本分数不能确认关系。

### 2.4 关系结论

- `已确认`：强键直接命中，或多项独立证据闭合且无硬冲突。
- `候选`：方向和主体成立，但仍缺分摊、节点或直接业务证据。
- `多候选`：两个以上真实候选无法可靠排除或分摊。
- `已拒绝`：记录具体硬冲突，防止以后反复吸附。
- `确认缺失`：应当存在该类资料，但在明确检索范围内未找到。
- `证据不足`：连业务性质或目标都无法稳定判断，写明所需证据。
- `业务不适用`：该业务本来不需要该流，不等于资料齐全。

确认关系使用真实关联字段；候选必须存入候选字段或候选状态，不能在界面上伪装成唯一确认。任何加权分数都只能排序候选，不能替代上述硬门。

## 3. 合同文件闭环

### 3.1 合同视觉分析和字段补全

逐页检查并填入合同专业表的实际对应字段：

- 合同名称、合同编号、合同类型、版本和来源文件；
- 甲乙双方及统一社会信用代码，必要时包括采购人、供应商、最终客户、代理方；
- 本公司法定主体、本公司角色、收款/付款方向；
- 项目名称、项目编号、地点、标段、品类、产品/服务明细和数量；
- 含税总价、未税金额、税率、币种、可调价条款和金额冲突；
- 签订日期、生效条件、有效期、履约期、交付地；
- 预付款、到货款、进度款、验收款、尾款和质保金的比例、金额、触发条件、到期计算基础；
- 发票类型、开票条件、税率和票款先后要求；
- 发货、到货、安装、调试、签收、验收、质保的责任和证明要求；
- 违约、退款、解除、变更和争议条款；
- 每方签字、印章、骑缝章和签章日期。

合同未载明的字段写“原文未载明”；页面模糊写“页面不可读”；版本缺页写“待找完整版本”。不得从项目惯例或其它合同补造本合同字段。

### 3.2 合同事实去重和版本归并

合同编号是强线索但不是唯一键。比较双方、金额、日期、项目、标的和条款：

- 同一合同的草案、单章版、双章版、扫描件和复印件归入一个版本组，但保留各自来源和生效状态。
- 同号不同年度、主体、金额或项目不得强并。
- 补充协议、变更协议和主合同分别建事实并关联，不覆盖主合同原金额。
- 投标文件、报价单、中标通知和采购需求不得冒充已签合同。

确定一条主合同事实参与计额；重复版本只扩充证据集合。

### 3.3 确定本公司角色和预期资金

先确认本公司是否是合同当事人。若本公司为卖方/服务方，预期本公司收款；若为买方/委托方，预期本公司付款。若文件只证明外部上下游项目链而本公司不是当事人，只可作为项目旁证，不可给本公司流水确认合同流。

### 3.4 合同反推银行流水和回单

合同入表后必须立即执行合同→资金反向搜索，不得等流水文件再次到来。

**第一步：建立应收/应付节点池。** 把每个付款条款拆成节点：节点名称、应付比例或金额、触发事件、理论最早/最晚日期、是否依赖发票/验收、质保到期和累计上限。条款不明确时只建立“总额待分摊”，不能自造节点。

**第二步：召回候选资金事实。** 在银行流水和单笔回单中组合查找：

1. 本公司主体和本公司银行账户必须对应。
2. 按本公司合同角色限定收入或支出方向。
3. 搜索合同对方完整名称、简称、已知账号；同时查文件中已证明的平台、代理或个人经办方。
4. 搜索合同编号、项目名、标段、品类、订单号、回单摘要和文件名映射。
5. 时间从合同签前有合理依据的保证金/预付款开始，到履约、验收、质保和解除后的退款结束。
6. 金额同时检查单笔合同总额、节点金额、比例金额、拆分付款、合并付款和累计净额，不只找完全相等金额。
7. 同时召回退款、冲正、账号误付、更正重付和手续费，计算净资金而非简单求和。

**第三步：硬排除。** 排除错误公司、错误方向、无依据第三方、摘要明确属于其它合同、业务日期不可能、项目/品类冲突和已全额占用的资金池。金额相等不能挽救这些冲突。

**第四步：逐个原件强审。** 对每个剩余候选同时打开合同主体/条款页和流水/回单原件，逐项核验：付款人、收款人、双方账号、方向、日期、金额、摘要、回单号、项目、节点条件及该笔款已被哪些合同占用。

**第五步：决定关系和分摊。**

- 回单摘要或文件名映射明确写合同号，主体方向不冲突时为最强信号。
- 对方账号、方向、日期和节点金额共同闭合，可确认到合同及节点。
- 对方相同但集中付款覆盖多份合同，只能在有分摊表、摘要、金额池唯一解或其它直接证据时确认分摊；否则保留多候选。
- 一份合同多笔付款分别关联并累计；不能因单笔小于合同额而拒绝。
- 一笔款覆盖多合同必须记录每份合同分摊金额，原流水只保留一条事实。
- 签前付款需要保证金、订单、审批或后续合同追认等证据；仅日期接近不能确认。
- 退款和冲正关联原交易，减少净收付，不新增长期经营额。

### 3.5 合同反推发票

合同入表后搜索发票表：先按本公司买卖角色限定进项/销项，再按合同双方或被证明的开票主体、品类/服务、合同生命周期、含税和未税金额池召回。逐张打开票面核验购销方、税号、日期、项目、金额和红蓝状态。

一张发票可覆盖多合同，一份合同可分期开票。只有分摊明确时计入确认开票金额；主体相同但金额无法分摊时保留候选。红字发票冲减对应蓝票；作废票不进入确认金额。不能用成本进项票满足销售合同的销项开票要求。

### 3.6 合同反推货物流和履约

按合同双方、项目、地点、品类、型号、数量、履约期和合同规定的交付/安装/验收节点召回货物流凭证。逐份打开原件核验发送方、接收方、签收人、日期、物项、数量、结论和印章。

外部最终客户的签收或巡检只证明项目链旁证时，不得自动升级为本公司与合同对方之间的直接履约。空白模板、未勾选验收单或仅有技术参数不能确认完成节点。

### 3.7 合同写入后的级联

更新或创建：合同专业表、合同关联资金/发票/履约、合同收付款审核、所属项目、项目流水汇总和涉及流水的四流一致审核。合同收付款审核至少重算合同额、已收/已付确认额、候选额、退款冲正、未结余额、下一节点、到期日、逾期、质保金和异常说明。

若财务重发把流水从旧合同改到新合同，保留流水和审核记录 ID，解除旧关系、建立新关系，并同时重算旧合同、新合同、两个项目汇总和该流水四流审核。

## 4. 银行流水文件闭环

### 4.1 拆成资金事实

遍历全部非空交易行，每行提取：本公司、银行、账号、交易日期时间、收入/支出方向、金额、余额、对方名称、对方账号、流水号/回单号、摘要、用途、币种和来源页/行。表头、期初余额和合计行不是交易事实。

对跨页重复、导出重叠和不同文件版本去重。事实强键优先使用银行流水号/回单号；没有时综合本公司账号、方向、时间、金额、对方账号和摘要。相同金额同日多笔不得误并。

### 4.2 与回单归并

先搜索单笔回单：流水号或回单号一致为强键；否则核验双方账号、方向、日期时间和金额。PDF/PNG别名只扩充同一资金事实证据，不重复计额。回单尚未进入系统时，流水事实仍可建立，并把回单流标为确认缺失或待补。

### 4.3 判断业务性质

Agent 查看摘要、双方主体、账号历史、项目线索和相邻冲正，区分购销、内部划转、贷款/还款、保证金、工资社保税费、报销、银行手续费、利息、退款/冲正和来源不明个人往来。不能先假设所有流水都需要合同、发票和货物流。

### 4.4 流水正推关系

对购销资金依次搜索：合同、发票、履约和项目。每类都执行广泛召回、硬排除、逐个原件核验。合同搜索使用本公司主体、对方、方向、日期生命周期、摘要强键、项目/品类、单笔及累计金额池；不能只按金额匹配。

对非购销资金搜索相应凭证：借款协议、内部账户、工资表、税单、费用审批、保证金依据或冲正原流水。四流表中不适用的流写“业务不适用”，同时写实际应补资料，不能留下空白。

### 4.5 流水级联

更新银行流水、单笔回单关系、合同/发票/履约候选或确认关系、项目归属、合同收付款审核、项目流水汇总和该笔四流一致审核。项目经营汇总只纳入确认的经营资金；候选、内部款、融资、税费、工资、手续费和冲正不得混入利润。

## 5. 单笔回单文件闭环

### 5.1 切割和字段提取

一个文件含多张回单时按回单边界切成派生对象，每张回单独立入单笔回单表并关联父文件。视觉提取付款人、收款人、双方账号、开户行、日期时间、金额、币种、流水号、回单号、用途摘要、回单章和状态。

### 5.2 找到或创建资金事实

先以流水号/回单号搜索银行流水；未命中时用本公司账号、方向、日期时间、金额、对方账号和摘要组合搜索。命中后给既有资金事实增加来源，不创建重复流水。确无流水表来源时可由回单建立资金事实，并明确来源仅为回单。

### 5.3 处理文件名映射

先解析文件名映射，再验证映射目标与原件主体、方向是否存在硬冲突。映射用于找到或纠正关系；它不允许把付款回单连到本公司应收合同，也不允许跨错误公司主体。

如果回单对应资金事实已经存在，保留原回单、流水和四流记录 ID，只更新关系。相同 SHA 重发的新映射是财务反馈事件，必须触发旧/新关系级联重算。

### 5.4 回单触发的全链搜索

完成回单→流水后，以该资金事实启动流水正推合同、发票、履约和项目搜索。对个人电子汇入等摘要不足对象，检查同账号历史、同日镜像、工资/报销/项目款线索，但不得仅凭姓名或金额强判；需要个人往来台账、记账凭证摘要、审批或收款说明时明确补件。

## 6. 发票文件闭环

### 6.1 发票事实提取

逐张提取发票代码/号码、种类、开票日期、购方及税号、销方及税号、货物或服务名称、规格、数量、单价、未税金额、税率、税额、价税合计、备注、红字信息、作废状态和来源。

一文件多票时拆成多事实。用发票号码、代码、主体和金额去重；查重不能只看文件 SHA。红票、蓝票和作废票分别保留并建立冲销关系。

### 6.2 确定本公司角色

本公司为购方则是进项候选，本公司为销方则是销项候选。主体不是本公司时，只能作为外部项目链或其它公司证据，不能填补本公司发票流。

### 6.3 发票反推合同

按购销双方、税号、品类/服务、开票日期与合同生命周期、价税金额池、合同开票条款、项目和文件名映射召回合同。排除错误公司角色、外部合同、品类冲突、日期不可能和已闭合占用。逐份打开合同主体、标的、金额和开票条款页，与票面逐项比较。

同主体集中开票可能覆盖多合同；无分摊证据时只能多候选。一份合同分期开票则逐票累计。不得因为发票总额等于某合同就越过主体、品类和时间硬门。

### 6.4 发票反推资金、履约和项目

按本公司角色确定预期收付款方向，搜索同双方、合理日期、金额池和项目的流水/回单。票款可先票后款、先款后票或分期，必须结合合同条款；金额不等不等于无关系。再按品类、数量、项目、地点和日期搜索履约凭证。

更新发票表、合同开票累计、项目开票收入/成本、对应流水四流审核和发票缺口。候选票不能计入已确认开票额。

## 7. 货物流与履约文件闭环

### 7.1 判断证据角色

区分直接履约事件和辅助资料：发货单、物流单、到货单、签收单、安装记录、调试记录、验收单、服务确认可形成事件；空白模板、技术参数、投标响应、产品手册、检测报告和证书通常只作支持证据，除非原件明确证明特定项目的特定交付。

### 7.2 履约事实提取

提取阶段、日期、发送/服务方、接收/验收方、项目、地点、合同号、品名、型号、序列号、数量、金额、签收人、签字、印章、勾选项、明确结论和来源页。申报数量大于影像能证明的数量时，只确认影像可证数量。

无签章不意味着没有稳定事实；但签章也不能补造空白日期、勾选项或“验收合格”结论。

### 7.3 履约反推合同

先用文件名合同映射和票面合同号召回，再按双方、本公司角色、项目、地点、品类、型号、数量、合同履约期和节点条款召回。逐个打开合同标的/履约条款页和履约原件。排除外部项目链、主体冲突、品类/型号冲突和生命周期不可能。

### 7.4 履约反推流水和回单

若文件名含 HD/回单或 LS/流水映射，直接定位目标事实并做主体方向硬门。无映射时，先通过已确认合同付款节点查找应触发的资金池，再按项目、对方、日期和节点金额召回流水。不得仅因为履约和流水同项目或同金额就确认直接关系。

一份文件含多个设备、批次或阶段时按事件边界拆事实。外部最终客户签收只能证明项目链旁证而缺本公司直接服务确认时，保持候选/间接证据。

### 7.5 履约级联

更新货物流凭证、合同履约阶段和付款触发条件、项目履约状态、相关流水四流审核、合同收付款审核下一节点。空白验收模板或结论为空时不得把合同节点标成已验收到期。

## 8. 项目及辅助资料闭环

### 8.1 项目身份

项目事实至少综合项目名称、编号、客户、地点、年度、标段和本公司角色。使用稳定项目唯一键检查重复；名称近似但客户或标段不同不得强并。

招标文件、中标通知、报价单、项目清单、技术方案和会议资料可建立项目身份或业务线索，但不能自动冒充合同、发票或履约事件。

### 8.2 项目反向搜索

新项目事实入表后，按项目号、标准化项目名、客户、地点、年度、品类和文件名项目映射搜索合同、流水/回单、发票及履约。逐个核验原件中项目指向；项目名只是弱线索时保留候选。

### 8.3 项目级联

项目流水汇总只纳入已确认归属的经营收入、经营成本、已确认发票和应收应付。候选关系单列，不进入毛利。外部项目链合同或最终客户验收可作为旁证，但不得替代本公司直接业务链。

## 9. 非购销及其它文件闭环

先识别真实业务性质，再决定应补资料，禁止强塞进购销四流：

- 同主体跨行划转：核验两端本公司账号和镜像流水，合同/发票/货物流不适用。
- 内部往来：核验关联公司、往来台账和用途；经营利润排除。
- 借款与还款：找借款合同、放款/还款计划和利息，不当作收入成本。
- 保证金：找项目/投标/履约保证依据和退回链，单独跟踪占用与退回。
- 工资、社保和税费：找工资表、申报表、缴款书或记账凭证，购销三流不适用。
- 报销和个人往来：找审批、费用单、个人台账和项目归属；无证据时保持来源不明。
- 银行手续费和利息：以银行流水/回单为主要证据，合同/发票/货物流通常不适用。
- 退款、冲正、账号误付和更正重付：关联原交易并计算净额，不能产生重复经营额。
- 无法判断的其它文件：文件索引保留，写明已读范围、无法形成何种事实以及下一证据。

四流审核对不适用项必须明确写“业务不适用”，总体结论同时保留该业务真正缺少的凭证类型。

## 10. 文件名映射处理

接受 `【键=值】` 和 `[KEY=value]`，键接受：合同/HT、回单/HD、流水/LS、发票/FP、货物流/WL、项目/XM。

- 映射键与文件内事实同类型：作为事实身份、版本归并或目标记录线索。
- 映射键指向其它类型：作为跨表关系强信号。
- 多个映射可同时出现，分别解析；不要求动作、版本或发送人字段。
- 映射目标精确唯一且原件无主体/方向硬冲突：建立或纠正关系。
- 映射目标不存在：保留事实，状态写映射未解析，并记录目标值。
- 映射命中多个事实：关联为多候选，等待合同号、回单号或其它强键消歧。
- 映射与原件硬冲突：不自动执行，记录冲突并保留财务反馈事件供人工复核。
- 一个文件含多个同类型事实而映射无法指明哪一个：不得把映射复制到全部事实。

映射纠错只改变关系，不删除重建既有事实。任何关系变更必须反向重算旧目标和正向重算新目标。

## 11. 多表级联矩阵

| 新增或变更事实 | 必须补全的专业表 | 必须主动搜索 | 必须级联的业务表 |
| --- | --- | --- | --- |
| 合同 | 合同 | 流水、回单、发票、货物流、项目 | 合同收付款审核、四流一致审核、项目、项目流水汇总 |
| 银行流水 | 银行流水 | 回单、合同、发票、货物流、项目及非购销凭证 | 四流一致审核、合同收付款审核、项目流水汇总 |
| 单笔回单 | 单笔回单、银行流水来源 | 流水、合同、发票、货物流、项目 | 四流一致审核、合同收付款审核、项目流水汇总 |
| 发票 | 发票 | 合同、流水、回单、货物流、项目 | 四流一致审核、合同开票状态、项目流水汇总 |
| 货物流/履约 | 货物流凭证 | 合同、流水、回单、发票、项目 | 四流一致审核、合同节点、合同收付款审核、项目履约 |
| 项目资料 | 项目或辅助证据 | 合同、流水、回单、发票、货物流 | 项目流水汇总及相关候选关系 |
| 非购销凭证 | 对应专业事实/文件索引 | 原资金事实、业务依据 | 四流一致审核的业务不适用及应补资料 |

级联依赖顺序通常为：文件索引→专业事实→事实去重→关系确认/候选→项目归属→合同收付款审核→项目流水汇总→四流一致审核。关系纠正时必须把旧关系的反向影响纳入同一 Action Plan。

## 12. 无匹配、多候选、冲突和补件处理

- 无候选：记录搜索过的表、主体、账号、编号、日期窗、金额池和关键词；区分“确认缺失”和“证据不足”。
- 单一弱候选：不能因候选唯一就确认；写缺少的强证据。
- 多候选：展示全部真实候选、每个支持证据和无法排除原因；金额不计入确认汇总。
- 字段冲突：保留各来源字段值和证据页，不用后到文件静默覆盖；判断是否为版本变更、红冲、补充协议或读取错误。
- 文件不可读：有限重试下载，并执行文本层、字体/表单/图像资源和第二渲染链路交叉检查；排除“视觉假空白”后仍失败，才记录真实错误和所需原件，不伪造 SHA、页面或事实。
- 专业表已有记录：优先补证据和字段，不机械新建；人工字段保持不变。

## 13. 生产写入与完成门

每个有界批次写入前：

1. Fresh-read 受影响记录和人工字段。
2. 保存字段级 before 快照、人工字段 hash 和回滚文件。
3. 校验每个事实的证据、去重、关系状态和级联 Action Plan。
4. 限定只写本批次明确字段，不全量覆盖记录。

写入后：

1. Fresh-read 每条专业事实、真实关联字段和业务表结果。
2. 检查双向关系、旧关系解除和旧/新汇总重算。
3. 幂等复跑必须为 delta=0。
4. 人工审核状态和审核意见 hash 不变。
5. 候选没有进入确认金额，副本没有重复计额。
6. 回滚证据可恢复真实 before 值。

一个文件只有在其全部稳定事实均完成专业表补全、所需正反向搜索、逐候选原件审查、业务表级联和回验后才算处理完成。没有新文件时不重复搜索已穷尽对象；必须留下检索范围、缺失证据和重新打开该对象的触发条件。
