## 规则复述

项目与项目流水汇总处理手册共十六章：

- **一、项目是什么**：项目是一组具有共同业务目标、交易背景和履约范围的业务对象，由招标/中标/合同/编号/映射等证据识别。项目不是文件夹、来源群、某公司全部业务、每笔流水都必然对应的项目。日常经营交易（手续费、利息、税费、房租等）可不强行归入项目。
- **二、新建项目条件**：须有可稳定识别的证据（原件项目全称、唯一编号、招标采购编号、中标通知、合同明确对应、强映射无硬冲突、多份证据共同指向）。只有模糊简称或单笔流水摘要时先形成候选、搜索已有，不立即新建。
- **三、唯一性与去重**：优先用编号/全称/采购人/最终用户/年份/标段/中标供应商等去重。须区分简称全称、不同标段、不同采购包、废标后重新招标、不同年度、同客户多项目、销售侧采购侧合同、总项目子项目、框架订单、更名、同名不同采购人。不能只按名称去重或只按交易对方合并。
- **四、名称和标识**：标准名称不能凭空改写，保留原文名称和历史别名。记录含名称/编号/标段/年度/地点/类型/状态/主体角色/采购人客户/供应商/最终用户/负责人/来源/创建依据/映射/缺失冲突等。
- **五、主体和角色**：一个项目可同时含本方销售/本方采购/客户/最终用户/上游供应商/代理机构/招标人/中标供应商/分包方/联合体成员/代收代付方。可有多份合同（销售/采购/分包/补充协议/订单/售后），不同合同不同主体金额不能混为同一事实，项目负责聚合合同保持独立。
- **六、生命周期**：19种状态从"线索"到"已完成/终止/未中标/废标流标/状态待确认"。状态不能只由一份文件标题决定——有中标通知只支持已中标待签，有单方盖章合同不能写已生效，有验收单结论为空不能写已验收合格，全款到账不一定项目完成。
- **七、关联内容**：项目应聚合文件索引/招投标/合同/流水/回单/发票/二维码/货物流/截图/流水汇总/收付款审核/四流审核/缺失/冲突。关系必须来自具体证据，不能只保存文字摘要。
- **八、新证据到来时的项目反查**：任何专业文件完成后都须检查项目关系，结论6种（已确认/高概率候选/可能跨多项目/无项目属性/明确排除/待人工确认），只有已确认写入正式关联。
- **九、跨项目事实**：保留原始完整事实，不复制创建多条相同流水发票，建立多项目候选或确认关系。需分摊时记录每项目分摊金额/数量/依据，合计等于原事实，无证据不平均分配，无法分摊标"跨项目未分配"，汇总只计算已确认分配部分。
- **十、项目流水汇总**：基于银行流水事实聚合形成的业务汇总表，不是新的流水事实表，不能手工复制流水金额。须服从现有表格业务键，不得自行改变粒度。
- **十一、计算范围**：纳入已确认外部收支/已确认分摊/明确相关退款冲正手续费/规则需纳入税费保证金；不直接纳入候选未确认/内部转账/已冲销净影响为零/重复记录/同一流水多份回单/未分配跨项目/无关手续费利息税费。
- **十二、汇总计算**：基础公式（累计收款=已确认收入流水之和-已确认退款支出等）工具可计算，但哪些流水属于项目/哪些退款对应原交易/哪些手续费计入项目/哪些需分摊/哪份合同收入侧成本侧/哪些异常排除由 Agent 判断，工具不能凭金额自动分项目。
- **十三、更新时机**：增量触发重算相关项目而非全表重算（新流水归属/纠正项目/分摊变化/退款冲正建立关系/内部转账识别/合同关联变化/合同金额付款节点变化/发票货物流补齐审核/重复流水合并），重算须固定范围→读唯一流水事实→排除重复证据→保存明细→fresh-read→再次计算验证。
- **十四、金额不能互相替代**：须分别保存预算/投标报价/中标/销售合同/采购合同/已开票/已收票/已收款/已付款/履约金额数量/项目成本/净现金流。不能用中标金额当收入、合同金额当已收款、发票金额当已付款、付款金额当已验收、预算当成本、净现金流当利润。
- **十五、动作清单**：至少17项。
- **十六、完成标准**：18项全部满足才算完成。

## 逐一回答

### 1. 什么是项目，什么不能被当成项目

**项目**是一组具有共同业务目标、交易背景和履约范围的业务对象。它可以由招标/采购项目、中标事项、一份或多份合同、同一客户的特定采购需求、同一最终用户的设备交付、同一建设/实施/服务任务、同一订单或采购批次、同一项目/招标/采购编号、或明确的[项目=...]映射来识别。

**不能被当成项目的**：文件夹、来源群、某家公司全部业务、某个交易对方全部往来、单纯相同金额、单纯相同文件名、每一笔流水、每一份合同都必然对应一个独立项目。日常经营交易（银行手续费、利息、日常税费、社保公积金、房租、普通办公采购、无项目属性的经常性服务）也不需要强行归入项目。

核心区别：项目是**业务事项**，不是文件容器或交易对方分组。一个项目可能跨越多份合同和多笔流水，而一笔流水也可能同时属于多个项目——关系由证据和判断决定，不是由物理归属决定。

### 2. 什么证据足以支持新建项目

至少应存在可以**稳定识别**项目的证据，包括：

- 原件明确写明项目全称
- 唯一项目编号
- 招标或采购编号
- 中标通知
- 合同明确对应项目
- 文件名或伴随文字提供项目强映射（[项目=...]）且无硬冲突
- 多份证据共同指向同一业务事项

只有模糊简称、单笔流水摘要或交易对方名称时，**不能**直接新建——应先形成项目候选，搜索已有项目，确认无匹配后再考虑新建。不得因"找不到项目"就给每个文件创建新项目，这会导致同一业务事项被拆成多个虚假项目，后续聚合和汇总全部失真。

### 3. 为什么不能只按项目名称去重

项目名称在不同文件中可能存在简称、别名、更名、不同标段后缀、不同年度后缀等情况。同一项目可能被写成"XX智慧城市项目""XX智慧城市（2024）""XX智慧城市一标段"等不同形式；不同项目也可能恰好同名但采购人、标段、年度不同。

只按名称去重会导致两类错误：
- **误合并**：把同名但不同采购人/不同标段/不同年度的不同项目合并成一个
- **误拆分**：把同一项目的不同写法当成不同项目

正确做法是综合编号（项目编号/招标编号/采购编号）、采购人/客户、最终用户、年份、标段/包号、中标供应商、合同编号、项目地点、采购内容等多维度判断。发现可能重复时，指定候选主项目，逐项对比，保留合并依据，未确认前不直接删除或合并。

### 4. 一个项目中多份销售和采购合同如何处理

一个项目可能同时包含本方与客户的**销售合同**、本方与上游供应商的**采购合同**、分包合同、补充协议、订单、售后服务合同等。这些合同的主体、金额、付款条件各不相同。

处理原则：
- **项目负责聚合，合同保持独立**——每份合同仍是独立的专业记录，有自己的编号、金额、付款节点和收付款审核
- **不能因同一项目就把不同合同、不同主体的金额混为同一事实**——销售合同金额是收入侧，采购合同金额是成本侧，分别记录
- 在项目流水汇总中，收入侧合同的收款和成本侧合同的付款分开计算
- 项目汇总的净现金流 = 累计收款 - 累计付款，但各合同的应收应付仍独立保留

典型场景：本公司中标一个项目后，与客户签销售合同（收入侧），同时向上游供应商采购设备（成本侧），可能还签了安装分包合同。三份合同都属于同一项目，但金额口径和收付款方向完全不同，绝不能混为同一事实。

### 5. 项目生命周期状态为什么不能由单一文件决定

因为项目生命周期是一个**跨阶段、跨证据类型**的递进过程，每个阶段需要不同类型的证据支持，单一文件只能证明其覆盖的那个节点：

- 有中标通知书 → 只能支持"已中标/待签合同"，不能跳到"合同已生效"
- 有单方盖章合同 → 不能直接写"合同已生效"（合同可能需要双方签章才生效）
- 有送货单 → 只能支持相应交付节点，不能跳到"已验收"
- 有验收单但结论为空 → 不能写"已验收合格"
- 全款到账 → 不一定代表项目已完成（可能还在质保期，或有未完成的售后义务）

项目完成需要综合判断：合同是否签署并生效、是否已履约交付、是否已验收合格、是否已开票、是否已收付款、质保条件是否满足。任何单一文件都只能支持其对应节点的状态，不能跨越中间环节直接得出终态结论。

### 6. 一笔流水跨多个项目时如何处理

现实中一笔银行流水可能同时支付多份合同、一张发票可能覆盖多个项目、一份采购合同可能服务多个销售项目。处理原则：

- **保留原始完整事实**——不拆分或复制创建多条相同流水或发票
- **建立多项目候选或确认关系**——同一流水可以同时关联多个项目，但关联状态（已确认/候选/待确认）分开记录
- **如需分摊**：记录每个项目的分摊金额、数量或依据，分摊金额合计必须等于原事实金额
- **没有证据时不得平均分配**——不能因为一笔流水关联两个项目就自动各算50%
- **无法分摊时**标记"跨项目未分配"
- **项目汇总只计算已确认分配部分**——候选或未分配的金额不纳入项目流水汇总

典型场景：一笔50万元付款同时支付项目A的30万元尾款和项目B的20万元预付款。需要依据合同付款节点、映射信息或伴随文字确定分摊依据，分别记录项目A分摊30万、项目B分摊20万。如果没有分摊依据，标记"跨项目未分配50万"，两个项目的汇总都不纳入这笔金额。

### 7. 项目流水汇总与银行流水事实表有什么区别

| 维度 | 银行流水事实表 | 项目流水汇总 |
|------|---------------|-------------|
| **性质** | 原始资金事实记录 | 基于事实聚合的业务汇总 |
| **数据来源** | 银行导出的交易明细/回单 | 已确认归属项目的流水事实 |
| **创建方式** | 逐笔提取和去重 | 按项目聚合求和 |
| **能否手工填写** | 不能手工复制流水金额 | 不能手工复制流水金额，须基于唯一事实计算 |
| **粒度** | 一行=一笔交易 | 一行=一个项目总体/项目+主体/项目+合同/项目+方向/项目+期间 |
| **去重** | 按业务键去重（流水号/参考号等） | 排除同一流水的多份回单证据、重复记录、内部转账 |
| **更新** | 新流水到来时逐笔处理 | 增量触发重算受影响项目 |

核心区别：流水事实表是**源**，项目流水汇总是**派生**。汇总不能创造新的资金事实，只能对已确认事实做聚合计算。汇总的准确性完全依赖于底层流水事实的完整性和归属判断的正确性。

### 8. 哪些流水可以纳入项目汇总，哪些不能直接纳入

**可以纳入**：
- 已确认属于该项目的外部收入流水
- 已确认属于该项目的外部支出流水
- 已确认分摊到该项目的部分金额
- 与项目明确相关的退款、冲正和手续费
- 规则明确需要纳入的税费或保证金

**不能直接纳入**：
- 只有项目候选但**未确认**的流水——候选关系不能产生汇总金额
- **内部账户转账**——资金在公司内部移动，不产生经营性收支
- 已被冲销且**净影响为零**的重复金额
- **重复流水记录**——同一事实的多条记录不能重复计额
- 同一流水的**多份回单证据**——回单是证据不是新事实
- **未分配的跨项目金额**——无法确认归属的部分不纳入任何项目
- 与项目**无关**的银行手续费、利息和税费

关键原则：是否纳入由 Agent 根据业务关系判断，计算工具只按 Agent 提供的已确认记录和规则求和。工具不能自行决定某笔流水"看起来像"某个项目就纳入。

### 9. 哪些判断由 Agent 完成，哪些计算可以交给工具

**由 Agent 判断（语义判断，不可委托工具）**：
- 哪些流水属于项目（基于合同/摘要/对方/映射等业务关系）
- 哪些退款对应原交易（冲销关系判断）
- 哪些手续费应计入项目（业务相关性判断）
- 哪些金额需要分摊、如何分摊（分摊依据和比例）
- 哪份合同属于收入侧或成本侧（合同角色判断）
- 哪些异常需要排除（重复/内部转账/冲销净影响为零）
- 项目状态判断（综合多份证据）
- 跨项目事实的归属和分摊

**可以交给工具（确定性计算）**：
- 累计收款 = 已确认收入流水之和 - 已确认退款支出
- 累计付款 = 已确认支出流水之和 - 已确认退款收入
- 净现金流 = 累计收款 - 累计付款
- 分摊金额合计校验
- 余额和笔数校验
- fresh-read 后重新计算验证一致性

分工边界：Agent 决定"哪些事实属于项目、怎么分"，工具负责"按确定规则求和验算"。工具不能凭金额自动分项目——这是业务判断，不是计算。

### 10. 为什么中标金额、合同金额、发票金额和收付款金额不能互相替代

这四类金额代表业务流程的不同阶段，性质和证据效力完全不同：

- **中标金额**是采购程序的结果金额，后续签合同时可能因谈判、补充协议等原因变化。用中标金额当累计收入会导致收入虚高或虚低。
- **合同金额**是双方正式约定的金额，但不等于已收款——合同可能分期付款、可能有预付/尾款/质保金扣减、可能存在违约或变更。用合同金额当已收款会高估实际资金流入。
- **发票金额**是已开票金额，但不等于已付款——存在已开票待付款、多票合并付款、红字退款等场景。用发票金额当已付款会高估实际资金流出。
- **收付款金额**是已发生的实际资金往来，但不等于已验收或已交付——付款可能早于交付（预付），交付可能早于付款（账期），验收可能晚于交付。用付款金额当已验收会错误判断履约状态。

此外，**项目净现金流也不能直接当利润**——利润还需扣除成本、税费、人工等，净现金流只是资金视角的净额。

核心原则：每种金额口径必须独立保存、独立追溯，在项目汇总中分别列示。金额之间的关系（如合同应收 vs 已收款 = 应收未收）是通过对比不同口径得出的分析结论，不是通过替代得出的。
