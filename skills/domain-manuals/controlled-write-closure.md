## 完整闭环复述

**写入闭环十步**：证据完成 → Agent 形成判断 → 搜索已有记录 → 生成动作清单 → 写前读取与快照 → 受控写入 → fresh-read → 业务验证 → 幂等复核 → 人类可读报告。任何一步未完成都不能宣称案件闭环。

**动作清单十一项必含**：action_id / case_id / 幂等键 / 目标 Base / 目标表 / 操作类型 / 目标 record_id 或新记录业务键 / 写前版本或修改时间 / 修改字段含每个字段旧值新值 / 核心判断依据 / 证据 record_id 或文件 token 或页码 / 关系置信状态 / 是否涉及人工字段 / 依赖动作 / 失败后处理方式 / 预期写后状态。

**操作类型十一类**：新建记录 / 更新字段 / 补充证据 / 建立关联 / 纠正关联 / 标记候选 / 标记排除 / 更新汇总 / 更新审核 / 记录缺口 / 记录冲突。

**写入九步顺序**：文件索引 → 专业集合记录 → 业务事实 → 证据关联 → 跨表关系 → 项目 → 项目流水汇总 → 合同收付款审核 → 四流一致审核。后续动作依赖前一步 record_id 时必须等前一步 fresh-read 通过，前一步失败时暂停依赖动作。

**写前 fresh-read 6 项**：当前目标记录 / 字段值 / 关联 / 人工字段 / 修改时间或版本 / 表字段结构。目的：发现财务人员刚改 / 其他 Agent 已处理 / 字段结构变 / 记录已不存在 / 候选关系已确认排除 / 动作清单已过期。不一致时重新分析差异更新动作清单，不直接覆盖。

**写前快照（更新）**：Base token / table_id / record_id / 写前完整字段 / 关联 / 人工字段 / 修改时间 / 快照时间 / action_id / case_id。新建记录也要保存预期业务键、写入字段、创建前搜索结果、记录数量。用途：对比、回滚、事故定位、幂等验证、审计。

**人工字段保护 9 类**：人工审核状态 / 人工确认 / 人工意见 / 财务备注 / 审批结果 / 人工指定关系 / 锁定字段 / 人工负责人 / 其他明确由人维护的字段。默认不覆盖非空人工字段；AI 与人工一致也不需重复覆盖；新证据写入 AI 建议或冲突字段；无专门字段时记录到动作报告不擅自改结构；只有明确授权才能改指定人工字段。

**新建幂等键 7 类**：文件索引（来源对象 ID/消息资源 ID/SHA256/派生来源+切割参数）/ 银行流水（本方账号/交易时间/方向/金额/流水号或参考号/对方账号）/ 合同（法人主体/合同编号/对方主体/项目/版本关系）/ 发票（代码+号码或数电票号/购销双方税号）/ 货物流（凭证编号/合同或项目/日期/批次/产品和数量）/ 项目（项目编号/招标采购编号/标段/主体/年份）/ 审核（现有表格业务键）。

**受控新建十步**：①按强业务键搜索 → ②按组合键搜索 → ③检查重复载体 → ④检查同一事实新增证据 → ⑤检查高概率重复 → ⑥确认无现有主记录 → ⑦保存创建前快照 → ⑧执行创建 → ⑨获得真实 record_id → ⑩fresh-read。

**受控更新九项**：精确 record_id / 只写清单列出的字段 / 不默认发送整行 / 不用空值覆盖稳定值 / 不用候选值覆盖已确认值 / 关系纠正保留原关系和纠正依据 / 证据列表合并不替换 / 多选字段保留无冲突现有值 / 修改前检查版本 / 写入失败停止依赖动作。

**关联双向 7 项确认**：两端记录真实存在 / 两端法人和业务角色合理 / 关系置信状态 / 是否已有关系 / 是否与人工关系冲突 / 是否需要双向字段 / 是否导致重复计数。关系纠正：保留事实主记录 / 记旧关联 / 记新关联 / 记纠正证据 / 标记排除候选 / 更新另一端 / 重算汇总和审核。

**写后 fresh-read 11 项**：记录存在 / 字段值与预期一致 / 数值类型正确 / 日期正确 / 多选值正确 / 附件链接有效 / 关联目标正确 / 双向关系成立 / 人工字段未变化 / 非目标字段未被修改 / 修改时间合理。

**业务验证 10 项**：是否生成重复事实 / 金额是否重复累计 / 收支方向 / 法人主体 / 合同编号进入正确字段 / 发票号码视觉一致 / 履约节点是否被过度判断 / 项目汇总是否只纳入确认事实 / 合同审核条件矩阵 / 四流总体状态是否符合四流分别状态。"字段写进去了"不等于"业务写对了"。

**幂等复核预期 8 项**：不新增第二条记录 / 不重复追加相同证据 / 不重复增加金额 / 不重复创建派生文件 / 不重复建立相同关系 / 不改变已正确字段 / 返回"已存在/无需变更" / 记录数和核心业务字段增量为零。

**远程结果不明恢复八步**：不立即重试 → 按业务键和预期 record_id 搜索 → fresh-read 远程状态 → 判断未写/全部写入/部分写入 → 更新动作清单 → 只补充缺失部分 → 再次 fresh-read → 记录事故和恢复过程。

**失败处理**：可重试：短暂网络错误/限流/临时不可用/读取超时。不可重试：字段不存在/类型错误/人工字段冲突/业务键重复/主体冲突/权限不足/远程结果未知/动作清单过期。失败记录 8 项：失败动作/已完成/未执行/远程实际状态/错误原因/部分写入/下一步证据/是否人工处理。

**回滚规则**：依据写前快照 + action_id + 写入回执 + fresh-read + 当前记录版本。新建记录确认无依赖才可删；有依赖优先标记撤销；更新只恢复本动作改的字段；不覆盖财务人员写入后的新修改；关系回滚检查两端；汇总审核重算；回滚后 fresh-read；回滚也必须幂等。未经明确授权不执行删除式回滚。

**并发多 Agent 8 项**：唯一 case_id / 每动作幂等键 / 写前检查记录版本 / 同一业务键只有一个写入者 / 其他 Agent 可读不可同改 / 已被更新时重新读取分析 / 不用旧快照覆盖新值 / 人工修改优先保护。

**动作回执 15 项**：action_id / case_id / Base / table_id / record_id / 操作类型 / 写前摘要 / 写后摘要 / 证据 / 判断依据 / 执行时间 / 远程返回 / fresh-read 结果 / 幂等结果 / 回滚定位 / 成功/部分成功/失败/待确认状态。"已发送请求"不能写成"成功"。

**案件完成门 10 项**：所有动作都有回执 / 依赖动作未跳过 / 无未知远程状态 / fresh-read 全过 / 业务验证过 / 幂等验证过 / 人工字段未覆盖 / 部分失败已明确处理 / 缺口和冲突已记录 / 人类可读报告完成。存在待人工确认：可标"处理完成，待人工确认"，不可标"审核通过"，不继续猜测补齐。

**十四类禁止**：无动作清单写表 / 不读原件写表 / 用过期 schema / 整行覆盖 / 用空值清除稳定事实 / 候选冒充确认 / 覆盖人工字段 / 未去重就新建事实 / API 成功即宣布完成 / 远程状态未知盲目重试 / 未经授权删除记录 / 只验证格式不验证业务 / 只验证首次写入不做幂等 / 用"正在处理"冒充进度。

## 十个问题回答

### 1. 完整写入闭环是什么

证据完成 → Agent 形成判断 → 搜索已有记录 → 生成动作清单 → 写前读取与快照 → 受控写入 → fresh-read → 业务验证 → 幂等复核 → 人类可读报告。这十步是一个完整的证据-判断-执行-验证闭环，每一步都有明确产物：动作清单是执行授权、写前快照是回滚基础、fresh-read 是状态真相、业务验证是语义正确、幂等复核是重复免疫、人类可读报告是审计交付。任何一步未完成都不能宣称案件闭环——"API 返回 200"只代表服务器接受了请求，不代表字段落表，不代表业务正确，不代表不会重复，不代表人工字段未覆盖，更不代表对方流程已更新。

### 2. 动作清单每一项必须包含什么

至少 16 项：action_id（全局唯一）/ case_id（案件唯一）/ 幂等键（去重和重试依据）/ 目标 Base 和 table_id（写入位置）/ 操作类型（11 类之一）/ 目标 record_id 或新记录业务键（定位对象）/ 写前版本或修改时间（用于乐观锁）/ 修改字段（精确到字段名）/ 每个字段的旧值和新值（diff 审计）/ 核心判断依据（语义逻辑）/ 证据（record_id / 文件 token / 页码或 sheet）/ 关系置信状态（强匹配/高概率/候选/排除等）/ 是否涉及人工字段（保护检查）/ 依赖动作（前序 action_id 链）/ 失败后处理方式（重试或回滚或人工）/ 预期写后状态（fresh-read 应看到的结果）。十几项跨表修改必须拆成十几个独立可审计的动作，不能打包成"写入全部结果"。

### 3. 为什么写前还要 fresh-read

写前 fresh-read 是为了发现"动作清单已经过期"的六类情况：①财务人员刚刚在另一个流程里修改了记录（比如把候选关系手动确认或排除）；②另一个 Agent 已经处理过同一案件并更新了字段；③字段结构发生变化（Base 加了列、删了列、换了字段类型）；④目标记录已被删除或合并；⑤候选关系已被人工确认或排除，AI 不能再用候选身份去关联；⑥原动作清单基于的是过期缓存或旧 schema。如果不 fresh-read 就直接按旧清单写入，会覆盖财务人员的手动修改、产生重复关系、把过期数据写进新结构——这些错误一旦发生就需要回滚甚至人工修复。写前 fresh-read 是把"计划写入"和"真实状态"对齐的最后机会，不一致必须先更新清单再执行。

### 4. 新建记录前如何决定改为更新

新建前必须经过 6 步搜索判断：①按强业务键（如合同编号、回单号、流水号、发票号码）精确搜索；②按组合键（如本方账号+日期+金额+方向）扩展搜索；③检查重复载体（同一文件的 PDF/PNG/扫描件/照片等不同形式）；④检查同一事实的新增证据（不同文件证明同一业务事实）；⑤检查高概率重复（金额相同主体相近日期不同的疑似重复）；⑥确认没有现有主记录。只有 6 步都通过才允许继续创建；任何一步发现已有记录，必须改为"更新"或"补充证据"，不继续创建。这是受控新建的核心——多数"创建"实际上是"补充"，无脑新建会污染业务事实层并破坏去重。

### 5. 为什么更新时不能默认发送整行

整行覆盖会引发三个严重问题：①把候选值或空值覆盖已经确认的稳定值（比如把人工确认的合同编号清空成空字符串）；②破坏未在动作清单中的字段（即便本次没动其他字段，API 可能因为 schema 校验把已有字段当成"未提供"而清空）；③把不属于本案件的人工新增修改覆盖掉（比如财务人员今天早上刚加的备注被 AI 的整行提交覆盖丢失）。正确做法是精确指定 record_id + 只写动作清单列出的字段 + 不用空值覆盖现有稳定值 + 不用候选值覆盖已确认值 + 多选字段保留无冲突现有值 + 证据列表采用合并而不是替换。每一次字段写入都必须有明确授权。

### 6. 关系纠正时需要保存和更新什么

需要做 7 件事：①保留业务事实主记录（流水事实不回滚，合同记录不删除，只动关联关系）；②记录旧关联（在动作清单和回执里保留"原关联=合同 A"作为审计证据）；③记录新关联（基于新映射和原件核验的"新关联=合同 B"）；④记录纠正证据（哪份回单、哪条伴随文字、哪份财务人员反馈触发了纠正）；⑤标记被排除的候选（在原合同记录上标记"已排除"或"已替换"，不能直接删除候选以免丢失历史关联痕迹）；⑥更新另一端（合同 B 的对应字段也要同步更新，双向关系必须两边都建立）；⑦重算受影响汇总和审核（项目流水汇总、合同收付款审核、四流一致审核都要因为关联变化重新计算）。被纠正的是关系不是事实，流水事实和合同事实本身是独立业务事实，纠正关系不能删流水重建。

### 7. fresh-read 后为什么还要做业务验证

fresh-read 只验证"字段是否落表、类型是否正确、关联是否双向成立、人工字段是否未覆盖"——这些都是"机器层正确"，但不等于"业务层正确"。业务层正确需要另外 10 项验证：①是否生成重复事实（同笔流水被写了两次、同一合同建了多份记录）；②金额是否重复累计（汇总表里同一金额被算了两次）；③收支方向是否正确（销项和进项、收入和支出没搞反）；④法人主体是否正确（合同主体和流水主体是否对应同一法人）；⑤合同编号是否进入正确字段（业务键没塞进备注、合同号没塞进对方户名）；⑥发票号码是否视觉一致（不是 OCR 误识的近似号码）；⑦履约节点是否被过度判断（验收单只有签收没盖章但被判终验合格）；⑧项目汇总是否只纳入已确认事实（候选未确认的不应计入）；⑨合同审核条件矩阵是否正确（条件状态、节点状态、缺什么证据都准确）；⑩四流总体状态是否符合四流分别状态（不能部分不适用但总体写一致）。"字段写进去了"不等于"业务写对了"——这是受控写入和普通写入的根本区别。

### 8. 幂等复核的远程业务结果应是什么

幂等复核不只是"action_id 不重复"，必须验证远程业务的实际结果。预期 8 项：①不新增第二条记录（按业务键搜索记录数不变）；②不重复追加相同证据（附件/链接列表不出现重复项）；③不重复增加金额（汇总表、累计字段、统计字段增量均为零）；④不重复创建派生文件（切割文件不出现新副本）；⑤不重复建立相同关系（关联记录数不变、新关联数=0）；⑥不改变已经正确的字段（fresh-read 后所有字段与首次执行后一致）；⑦返回"已存在/无需变更"语义（系统应能识别这是重复操作并跳过）；⑧记录数和核心业务字段增量为零（最严格的远程业务验证）。幂等检查不是简单比较 action_id 是否执行过——同一 action_id 因部分失败可被重试、同一业务键可能因 schema 变更需要重新执行、必须验证远程业务的实际结果而不是执行历史。

### 9. 远程结果不明确时正确恢复顺序是什么

请求超时/连接断开/返回体缺失/部分字段成功/关联写入状态不明/工具进程中断这六类情况都属于"远程结果不明确"，正确恢复八步：①不立即重试（盲重试会制造重复事实，先确认状态）；②按业务键和预期 record_id 搜索（用业务键找到目标记录的位置）；③fresh-read 远程状态（重新读取当前真实情况）；④判断三种可能：未写（什么字段都没落）/ 全部写入（部分成功但其实都已落）/ 部分写入（部分字段落了部分没落）；⑤更新动作清单（标记已完成项、未完成项、待补充项）；⑥只补充缺失部分（不是重写整行、不是覆盖已有部分）；⑦再次 fresh-read（确认补充成功）；⑧记录事故和恢复过程（在动作报告里写明"原写入超时、恢复时已确认 X 字段已落、补充了 Y 字段"）。盲目重试可能在已有部分数据上再次写入，产生字段覆盖或重复关系，这种错误极难清理。

### 10. 多 Agent 并发时如何避免互相覆盖

8 项保护措施：①每个案件有唯一 case_id（不同 Agent 处理不同案件不冲突）；②每个动作有幂等键（同一动作被多个 Agent 重复执行能识别为重复）；③写入前检查记录版本/修改时间（乐观锁，发现版本不一致就重新读取分析）；④同一业务键只能有一个写入者（不同 Agent 不会同时修改同一记录的同一字段）；⑤其他 Agent 可以读取但不能同时修改同一记录（共享读、独占写）；⑥发现记录已被更新时重新读取和分析（不能基于旧动作清单继续执行）；⑦不用旧快照覆盖新值（即便本地有写前快照，如果发现远程记录已被人工或其他 Agent 更新，应放弃旧计划重新评估）；⑧人工修改优先保护（任何 Agent 的写入都不能覆盖人工字段，即便看起来"自动修正"也不行）。在并发环境下，读取优先、写入独占、版本检查、冲突重新评估是基本纪律。
